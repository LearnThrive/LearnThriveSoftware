# Voice mode benchmark

Generated by `apps/web/scripts/voice-bench.mjs` (and `services/voice/bench.py`) on 2026-10-21 (plan19 section 5.4). Raw numbers: `docs/benchmarks/voice-engines.json`, `docs/benchmarks/voice-pipeline.json`.

> **Every recording here is synthetic.** The phrases were spoken by text-to-speech voices (never a child, never a real recording), so recognition scores are **optimistic**: a child's voice, a classroom's noise and an unfamiliar accent are harder. The owner's own recordings of real phrases, added to `tests/fixtures/assistant/voice-phrases.json` as WAV files, would be better evidence. Nothing here was heard by a person.

## The set

30 phrases of the kind a student says (maths and science vocabulary: x squared, quadratic, denominator, photosynthesis…), each spoken by 7 synthetic voices (kokoro-bf_emma, kokoro-bm_george, piper-en_GB-alba-medium, piper-en_GB-jenny_dioco-medium, piper-en_GB-northern_english_male-medium, sapi-hazel, sapi-zira), once clean and once with white noise added at 15 dB signal-to-noise. Word error rate is computed after folding digits to words ("5x" and "five x" are the same) and punctuation away. "Terms found" is the share of the maths and science words that were recognised correctly.

## The whole pipeline, end of speech to first audio

The speech sidecar and Ollama (`qwen3.5:9b`, voice-mode prompt) as the site uses them, 8 utterances per configuration after a warm-up. "End of speech" is the moment the recording stops; the clock stops when the first clip of speech has been synthesised (the browser then starts playing it, a few milliseconds). The model's first spoken chunk is the first complete sentence of at least 24 characters, as the page speaks it. The hop through the Next route adds a few milliseconds and is not included.

| Recogniser | Recognition (target < 700) | First model token (target < 1000) | First sentence ready | First speech clip (target < 500) | **End of speech to first audio (target median < 2500)** | p95 | VRAM in use |
| --- | --- | --- | --- | --- | --- | --- | --- |
| base.en/cpu | 588 ms | 370 ms | 722 ms | 204 ms | **1610 ms** | 1716 ms | 6601 MB |
| small.en/cuda | 151 ms | 354 ms | 595 ms | 162 ms | **908 ms** | 1191 ms | 7317 MB |

Median 908 ms against a target of 2500 ms: **met**. Most of it is the model producing a full first sentence, not the speech engines.

## Decision

- **Recognition: faster-whisper `small.en`, cuda, float16**: within a point of the best clean word error rate (1.8%), median 119 ms a clip, and on the GPU.
- **Without a usable GPU: `base.en` on the CPU, int8**: the most accurate CPU configuration under 700 ms a clip (4.6% word error, 546 ms). The sidecar chooses between the two itself (`VOICE_STT_DEVICE=auto`, the default): the GPU one if CUDA loads, the CPU one if not. The pipeline table shows the language model's first token is unchanged by the recogniser sharing the GPU (about 0.6 GB of VRAM).
- **Speech output: Piper.** Every Piper voice synthesises its first chunk in 72 to 98 ms against a target of 500, so the speed difference between them is noise; the default stays `en_GB-alba-medium` and the choice of voice is the owner's, by ear. Kokoro is often judged more natural but misses the 500 ms target on this CPU (750 ms and up).
- The browser's `speechSynthesis` stays as the automatic fallback when the speech service is unreachable.
- Push-to-talk only. Hands-free voice-activity detection was not built: it needs a measured false-trigger rate in a real room, and the first version should not listen when nobody pressed anything.

### What would change it

- A real child's voice and a real room: rerun with recordings. If word error rate is much worse than here, the next step is `medium.en` on the GPU (on the CPU it took 4.7 s a clip; it was not measured on the GPU here).
- A different machine: the CPU timings are for this CPU. A slower school-lab or hosted machine needs the numbers again.
- A hosted speech provider (a processor for a child's voice) is a plan19 section 6 decision; this report does not cover one.
- Running the language model and the recogniser on one 8 GB GPU is possible (see the VRAM column: the whole GPU, desktop included, was at about 7.3 of 8 GB with the recogniser on it) but leaves little room, so a second large program on the GPU would push the language model into system memory and slow it. CPU recognition (`VOICE_STT_DEVICE=cpu`) avoids the contest at a cost in accuracy.

## Reproduce

```bash
cd services/voice && uv sync && uv run python -m piper.download_voices --download-dir models en_GB-alba-medium en_GB-jenny_dioco-medium en_GB-northern_english_male-medium
cd ../../apps/web && npm run voice:bench -- --stt base.en/cpu,base.en/cuda
```

Kokoro needs `kokoro-v1.0.onnx` and `voices-v1.0.bin` from the kokoro-onnx release in `services/voice/models`; the CUDA runs need `uv pip install nvidia-cublas-cu12 nvidia-cudnn-cu12`. Models are downloaded from their publishers' hosts and are not committed.
