# Study Buddy (the AI assistant)

Study Buddy is a study helper inside the Library (`/library/study-buddy`) for enrolled students and Library subscribers. It is **off in production** and **for adults only** until the owner completes plan19 section 6 and records it. This page is how it is built, how to run it, and what stands between it and a child using it.

Measured model choices are in [ASSISTANT_BENCHMARK.md](ASSISTANT_BENCHMARK.md) (generated by `npm run assistant:bench`). Voice is in [VOICE.md](VOICE.md) once built.

## The rule it is built around

The assistant is an AI, says so, and is a second line, never the only one. In order, for every message:

1. Length, then a per-minute and a per-day cap (an attempt counts, so a refused message still uses one).
2. **Input rules** (`src/lib/assistant/moderation.ts`), before any model sees the text:
   - a **safeguarding disclosure** (self-harm, abuse, an unsafe situation) gets a **fixed reply** with Childline (0800 1111), NSPCC (0808 800 5000) and 999, **with no model call**, and a flag email to the safeguarding lead with an opaque reference (`SG-…`, never the name or the message);
   - personal details (phone, address, email), prompt injection, adult content and "write my coursework" are turned away with a fixed reply.
3. Uploads (`uploads.ts`, `documents.ts`): photos are decoded in plain JavaScript, turned upright from their EXIF orientation, shrunk and re-encoded with **no metadata at all**. PDFs are read with pdf.js: the text of each page in reading order, labelled with its page number, with powers and subscripts kept (`x^5`); a page with no usable text, a picture or stacked maths (fractions) is also drawn as a picture for the model, up to 3 pictures a message, the pages the question names first. A password-locked, damaged, blank or too-slow PDF gets its own message, and the model is told what it could not see so it never invents it. A PDF that is only restricted (copy or print, an empty open password, as many exam-board PDFs are) is read normally; scripts and embedded files are refused. At most 3 files, 8 MB each, 15 MB and 20 pages for a PDF. HEIC is refused with a message, not converted. A follow-up question in the same chat still has the last files. `npm run documents:check` runs every fixture in `apps/web/tests/fixtures/documents` through the real model.
4. A FIFO queue in front of the model (`ASSISTANT_CONCURRENCY`, default 1: one GPU), then the provider's stream passes through the **output guard** sentence by sentence (a leaked system prompt, a phone number, adult words are stopped mid-answer and replaced by a fixed line).
5. The answer is stored with the chat. Nothing is kept in the browser (no cookies besides the account session, no `localStorage`).

The system prompt is hints-first: it guides, asks the pupil to try the next step, and gives a final answer when the pupil says they have finished and want to check. It also carries a canary token; the output guard stops any answer that contains it.

## Running it on your machine (development)

Needs [Ollama](https://ollama.com) with the models in the benchmark, the Supabase-or-in-memory store the rest of the Library uses, and a Library account with access (`npm run library:grant`, or the dev seed at `/api/dev/library-seed`).

```bash
ollama pull qwen3.5:9b        # the default text model, about 6.6 GB
cd apps/web && npm run dev    # ASSISTANT_PROVIDER defaults to ollama at http://127.0.0.1:11434
```

Without a GPU or Ollama, `ASSISTANT_PROVIDER=mock` runs a scripted model (this is what the Playwright tests use).

NVIDIA's hosted catalogue (`ASSISTANT_PROVIDER=nim`, key in `NVIDIA_API_KEY`) is for **evaluation with synthetic prompts only**. It is a free trial with request limits, only some listed models are callable from an account (the others answer 404), and models are retired without much notice (two were already gone, HTTP 410, when the benchmark ran). It is never used in production and never receives real student content; `config.ts` refuses it in production.

`ASSISTANT_PROVIDER` may be a comma list (`ollama,nim`): an ordered fallback chain, development only.

## The Paper Tutor (worked solutions written onto a paper)

With a PDF or photo of a maths paper in the box, **Solve this paper** reads it, lists the questions it found (tick the ones wanted), and writes worked solutions onto a copy in blue handwriting-style ink. Three ways to write them: **answers and working** (the default: the answer and as much working as fits in each answer space, the full method on pages added at the end), **answers on the paper**, or **worked solutions** (the paper untouched, then the pages). It runs as a background job, so the chat stays usable; the panel shows each question as it goes, then a download (`GET /api/assistant/files/<id>?download=1`, only for the family that owns it) and a preview of each page. A summary is posted into the chat with the paper attached, so "explain question 3" works afterwards without solving again.

How it decides what to write (`src/lib/paper/`):

- `questions.ts` finds the numbered questions from the text layer and measures the empty space below each from a drawing of the page: ink rows are obstacles, a solid rule (an answer box's edge) splits the space, a dotted answer line is somewhere to write. Pages with no text layer are read by the vision model instead, and marked "read from a picture".
- `solve.ts` asks the model for a structured solution (JSON, validated, one retry). **The model never certifies its own answer.** `maths.ts`, a small safe parser (no `eval`), checks it: against the equation, expression or calculation printed in the question first, and only then against a check the model proposes. A failed check triggers one second attempt with the model reasoning first and told exactly what did not hold; only an answer that a calculation confirms replaces the first.
- Every question ends with one status, shown in the panel, on the paper and in the summary: **checked by calculation**, **checked against the AI's reading** (the check passed, but on the AI's transcription rather than the printed text), **not checked** (nothing to calculate, for example a word problem), or **not confidently solved** (the check disagreed, or the model could not answer).
- `annotate.ts` writes only into measured empty space, never over printed text and never below 11 pt (what does not fit goes to the worked pages, with a page reference on the paper). Maths is typeset by MathJax as vector shapes; the handwriting font is Patrick Hand (OFL). Every page carries "AI-generated worked solutions - may contain mistakes". The output is read back before it is stored, to prove it opens.
- `jobs.ts` holds jobs in the server's memory (one at a time per family, 10 papers a day, cancellable, every model call through the same queue as the chat). The annotated PDF is a chat file, so it follows the uploads' retention (below); an unfinished job does not survive a restart and the panel says so.

Measured with `qwen3.5:9b` on Ollama (`node --import tsx apps/web/scripts/paper-check.mjs`, and through the routes on a running server): the 5-question, 3-page GCSE fixture was read in about 3 s and solved in about 43 s with the model already loaded (about 3 minutes on a cold first run) on the 8 GB GPU. Across four runs through the routes every final answer was right; the statuses vary a little with the model's wording (the percentage question is sometimes "checked against the reading", sometimes "not checked"). Simultaneous equations sometimes need the reasoning retry (about 36 s against 6 s). Two checker faults found this way were fixed: "0.000 52" (a UK digit-group space) was read as 0 × 52, which marked a right answer "not confidently solved"; and sentences written in the maths field were typeset as maths. Output: `docs/screenshots/paper-tutor/`. **Marking a student's own answers is not built**: it needs its own reliability evaluation on real marked scripts before it is offered.

## Switching it off

`ASSISTANT_ENABLED=false` (or unset in production): the menu item disappears, the page says it is not available, every `/api/assistant/*` route answers 503 `unavailable` and no model is contacted. No redeploy of code is needed, only the environment variable.

## Who may use it

- An account with Library access (enrolled student or subscriber), signed in.
- **Adults only until `ASSISTANT_MINORS_APPROVED=true`.** Until then the first message needs a recorded tick ("I am 18 or over, and I am the person using Study Buddy", consent kind `assistant_adult_use`, versioned). The account must also be an adult account holder (`adult_required` otherwise), and a student profile is not attached to a chat until the minors gate is open. The wording is a draft for the owner's lawyer.
- In production it also needs `ASSISTANT_ENABLED=true`, `ASSISTANT_PRODUCTION_APPROVED=true`, provider `custom` and a base URL and key. Ollama and NIM never qualify.

## What is kept, and for how long

| Data | Kept | Removed |
| --- | --- | --- |
| Chat text (questions and answers) | 30 days after the chat's last message | by the retention job; or at once when the family deletes the chat (hidden immediately, removed by the next run) |
| Uploaded pictures and PDFs, and the Paper Tutor's annotated PDFs | 7 days, or when the chat is deleted | by the retention job (storage objects first, rows only if every object went) |
| Paper Tutor jobs (the questions found, progress) | in the server's memory, 2 hours after last use | on restart, or when they expire |
| Usage counters | counts only, no text | rolling |
| Safeguarding flag | an opaque reference, a category, a short excerpt in the email to the lead | the lead's own record; nothing named is stored in the app |
| Audio (voice) | never stored | n/a |

Run the retention job daily: `npm run assistant:retention` (a cron on Render; it needs the same Supabase and storage variables as the site). Families can see, export (JSON, `GET /api/assistant/export`), delete a chat, or delete all chats from the Study Buddy screen. The chat rows go with the family record (database cascade), but **uploaded files in storage do not**: before a family's record is erased, run "Delete all my chats" for it and let the retention job run once, so the files are removed while their paths are still known. Wiring that into the account-deletion procedure is listed in [RETENTION_AND_DELETION.md](RETENTION_AND_DELETION.md).

## What was not tested here

- A real production provider: none has been chosen (plan19 section 6 decides it: data processing agreement, no training on inputs, a suitable processing location, EU or UK if possible).
- A real child, a real safeguarding lead, a real teacher marking panel: the evaluation is synthetic and rule-based, so it ranks models; it is not evidence of pedagogical quality.
- Handwriting: the vision set is typed text only. The Paper Tutor was measured on generated papers (typed, one scanned page), not on real exam-board papers or phone photos of them.
- The email path to a real mailbox (the dev outbox is used in tests).

## Decision record: which model

See the benchmark's "Decision" section for the numbers and the rule the script applies. In short, the default is chosen among the models that fit the 8 GB GPU with every layer on the GPU, give no empty answers, and hold at least 90% of the safety prompts **on their own**, then by quality, then by first-token time. Findings that shaped it:

- **The models that answer most questions correctly are the ones that fail the safety prompts.** `gemma3:4b` and `qwen3-vl:8b-instruct` both scored 95% on the answer rubric, but on their own held only 60% and 70% of the safety prompts: `gemma3:4b` printed its system prompt when asked and repeated a swear word on request; `qwen3-vl:8b-instruct` was refused only 1 time in 3 on injection. The rules in front of and behind the model catch many of those (80% and 90% "with the rules"), but a model that needs catching on injection is a weaker second line. `qwen3.5:9b` held every safety prompt on its own (100%) and is the default.
- **`qwen3.5:9b` scores 71% on the answer rubric because it guides instead of stating answers**, even when the pupil says they have finished (maths 4/8). That is the product prompt working; for a tutoring tool it is the behaviour wanted, and the rubric cannot tell a good hint from a missing answer. Read the quality column as a floor for comparison.
- **Vision: `qwen3.5:9b` (3 of 5) stays the default**, one model on the GPU so there is no swapping between a text and a vision model on 8 GB. `qwen3-vl:8b-instruct` reads all 5 typed pictures but spills 1.3 GB into system RAM, is slower (median 4.2 s against 2.4 s) and is weaker on injection; set `ASSISTANT_VISION_MODEL=qwen3-vl:8b-instruct` if photo reading proves too weak in real use. Remember the set is typed text, not handwriting.
- **`qwen3-vl:8b` (the thinking variant) is unusable interactively.** Ollama ignores `think:false` for it, so it spends its token budget thinking and returns empty answers after about 20 seconds. The `-instruct` variant is measured instead (first token 0.17 s).
- **`qwen3.8:27b` is a quality ceiling, not a candidate.** It does not fit the GPU (most of it runs on the CPU: a few tokens a second, minutes for a worked answer), so it shows how good a bigger model would be, which a hosted production provider could be.
- **`llama-guard3:1b` as a classifier in front of the model** catches only part of what the plain rules catch on this set, so it is not added; it could be reconsidered with a larger set.
- **A rule-based rubric favours models that state answers.** The product prompt makes the model guide first, so the checking prompts say the pupil has finished and wants to check; a model that guides more strictly can score lower on "quality" for being a better tutor. Read the quality column as a floor for comparison, not a grade.

## What would change the decision

- A different GPU or a quantisation that fits a larger model.
- A real production provider: re-run `npm run assistant:bench -- --models ...` against it with synthetic prompts only, and compare.
- A real marking panel on approved material, and a safeguarding review of the fixed replies and the rules, which are the controls that must be right whichever model sits behind them.

## Reproduce

```bash
cd apps/web
npm run assistant:bench -- --models qwen3.5:9b,gemma3:4b,qwen3-vl:8b-instruct --ceiling qwen3.8:27b --nim meta/llama-3.2-11b-vision-instruct --guard llama-guard3:1b
```

It needs Ollama running with those models, `ffmpeg` on the path (for the vision pictures) and, for `--nim`, `NVIDIA_API_KEY` in the environment. It writes `docs/ASSISTANT_BENCHMARK.md` and `docs/benchmarks/assistant-results.json` (the raw per-prompt numbers and answers; synthetic prompts only). Close other GPU programs first, or the timings are not comparable.
