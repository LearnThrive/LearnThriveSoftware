# LearnThrive AI (the AI assistant)

LearnThrive AI is a study helper inside the Library (`/library/ai`) for enrolled students and Library subscribers. It is **off in production** and **for adults only** until the owner completes plan19 section 6 and records it. This page is how it is built, how to run it, and what stands between it and a child using it.

During development the only reasoning model is **Reflection's Beam, served by Ollama Cloud** (`https://ollama.com/v1`, model `beam`), and answers can be **interactive interfaces** drawn with OpenUI as well as text: see [OPENUI.md](OPENUI.md). Nothing runs on the developer's GPU. The local models, NVIDIA's hosted catalogue and the developer model picker that came before are gone; [ASSISTANT_BENCHMARK.md](ASSISTANT_BENCHMARK.md) and [OLLAMA_THREE_MODEL.md](OLLAMA_THREE_MODEL.md) are kept as the record of that earlier evaluation. Voice is in [VOICE.md](VOICE.md).

## The rule it is built around

The assistant is an AI, says so, and is a second line, never the only one. In order, for every message:

1. Length, then a per-minute and a per-day cap (an attempt counts, so a refused message still uses one).
2. **Input rules** (`src/lib/assistant/moderation.ts`), before any model sees the text:
   - a **safeguarding disclosure** (self-harm, abuse, an unsafe situation) gets a **fixed reply** with Childline (0800 1111), NSPCC (0808 800 5000) and 999, **with no model call**, and a flag email to the safeguarding lead with an opaque reference (`SG-…`, never the name or the message);
   - personal details (phone, address, email), prompt injection, adult content and "write my coursework" are turned away with a fixed reply.
3. Uploads (`uploads.ts`, `documents.ts`): photos are decoded in plain JavaScript, turned upright from their EXIF orientation, shrunk and re-encoded with **no metadata at all**. PDFs are read with pdf.js: the text of each page in reading order, labelled with its page number, with powers and subscripts kept (`x^5`); a page with no usable text, a picture or stacked maths (fractions) is also drawn as a picture for the model, up to 3 pictures a message, the pages the question names first. A password-locked, damaged, blank or too-slow PDF gets its own message, and the model is told what it could not see so it never invents it. A PDF that is only restricted (copy or print, an empty open password, as many exam-board PDFs are) is read normally; scripts and embedded files are refused. At most 3 files, 8 MB each, 15 MB and 20 pages for a PDF. HEIC is refused with a message, not converted. A follow-up question in the same chat still has the last files, but not their pictures: what the document said is stored once and reused, and only an explicit "look at the diagram on page 2" re-renders one page (three-model brief, section 11). `npm run documents:check` runs every fixture in `apps/web/tests/fixtures/documents` through the real model.
4. A FIFO queue in front of the model (`ASSISTANT_CONCURRENCY`, default 2), then the provider's stream passes through the **output guard** sentence by sentence (a leaked system prompt, a phone number, adult words are stopped mid-answer and replaced by a fixed line).
5. The answer is stored with the chat. Nothing is kept in the browser (no cookies besides the account session, no `localStorage`).

The system prompt is hints-first: it guides, asks the pupil to try the next step, and gives a final answer when the pupil says they have finished and want to check. It also carries a canary token; the output guard stops any answer that contains it.

## Running it on your machine (development)

You need an **Ollama Cloud API key** (a free Ollama account: ollama.com/settings/keys), the Supabase-or-in-memory store the rest of the Library uses, and a Library account with access (`npm run library:grant`, or the dev seed at `/api/dev/library-seed`). There is no model to download and no GPU to feed: `npm run dev` starts the voice sidecar, web search, the page reader and the local Supabase stack (it never loads a model), and the website.

```bash
# in your own environment, never in a file that is committed (the key is a secret):
#   OLLAMA_API_KEY=<your key>
cd apps/web && npm run dev     # ASSISTANT_PROVIDER defaults to ollama_cloud, ASSISTANT_MODEL to beam
```

- `ASSISTANT_PROVIDER=ollama_cloud` (the default) sends chat requests to `OLLAMA_CLOUD_BASE_URL` (default `https://ollama.com/v1`, OpenAI-compatible) with the key in a header and the model `beam`. It builds only when `OLLAMA_API_KEY` is set; without it the assistant says it is not available. It is **development only**: in production it is refused and only the approved `custom` provider can open the assistant.
- `ASSISTANT_PROVIDER=mock` runs a scripted model (this is what the Playwright and unit tests use). It writes scripted interactive answers too, so the whole interface path can be exercised with no key and no network.
- There is **one** provider and **one** model. A comma list is refused (the assistant stays closed), a request that names a model or an effort is refused with 400, and if Beam fails the student is told it failed: no other model ever answers in its place.
- Beam reads **text only**. A photo or a scanned page is not sent anywhere: the student is told so and asked to type the question or upload a PDF with selectable text. A text-based PDF is read as text, as before.
- Beam's catalogue entry (checked 30 October 2026 against `https://ollama.com/api/tags`): name `beam`, capabilities `completion`, `thinking` and `tools`. Ollama's OpenAI-compatible endpoint takes `reasoning_effort` (used: "none" for plain chat, up to "high" for a hard problem, dropped for the next request if refused) and does not support `tool_choice` (so it is not sent).
- Usage is counted from the `usage` the endpoint reports (`stream_options.include_usage`); if a reply carries none, the visible answer's length stands in, so the per-account daily token budget (`ASSISTANT_DAILY_TOKEN_BUDGET`) still counts the turn.
- Web research uses Ollama's own web search and page reader when the key is set (docs/RESEARCH.md), and falls back to SearXNG and Crawl4AI.

Retrieval over a student's own uploads needed a local embedding model and is **off** (`ASSISTANT_RETRIEVAL`) until a hosted embedder is chosen; the most recent uploads are still read as text for the next question. The local "decision" and "recall" helper models are gone: routing is deterministic.

## Subject-aware answers, exam accuracy and web research

LearnThrive AI detects what the student is doing and for which exam, checks quotations before it answers, looks over the reply afterwards, and looks things up through SearXNG, which is always on (`npm start` runs it). All of it is described in [RESEARCH.md](RESEARCH.md). Two of those checks are worth naming here: the research block's sources are **numbered**, and the model is asked to write the number beside any passage it quotes (`[[cite:2]]`), so the server checks that quotation against the page the model named — one it has already read — instead of searching for words it cannot place; and an optional **recall** stage (`ASSISTANT_CLAIM_RECALL`, off by default, development only) asks a model where in the pages read a statement is settled in other words, so a claim is judged by meaning and not only by shared words. The marker is a claim about where the words came from and never proof they are there, and every span the recall stage proposes is located in the page word for word, in code, before it counts: neither can make anything verified on the model's word.

## Interactive answers (OpenUI)

When a message asks for something that works better as an interface than a paragraph (`Quiz me on photosynthesis`, `Plot y = x² and let me move it`, `Compare Remains and War Photographer`, flashcards, a diagram, a timeline, revealing a worked solution one step at a time), the answer can be a checked, interactive interface instead of text. An ordinary question is answered in words, a student who asks for words gets words, and a spoken turn never gets an interface. The design, the component library, the validation, the quotation checks, the security boundary and the tests are in [OPENUI.md](OPENUI.md).

## Activity panel (what LearnThrive AI did, and when an answer is shown)

While LearnThrive AI prepares an answer the student sees **one** progress interface, inside the assistant's own message, built only from work the server really did. Nothing is shown for show: no percentages, no invented steps, no hidden reasoning. (The old line under the box, three dots and "Thinking", was drawn by `components/ui/AiInput.tsx` itself, from the same busy state, and has been removed at its source: the JSX, its refs and motion hooks, and its CSS. The box now takes no part in showing progress. The page has one polite announcer, and the panel is not a live region.)

**Events.** The chat stream (`POST /api/assistant/chat`, one JSON object per line) carries typed `activity` events next to `delta`: `{ type: "activity", step: { id, kind, state, label, detail?, source? } }`. A step is announced as `running` and updated with the same `id` as `done` or `failed`. Kinds: `analyse` (what the question was taken to be), `document` (reading what was sent, or searching the family's own uploads), `search`, `read` (a page), `verify`, `calculate`, `repair` (the draft was corrected before release) and `write` (bookkeeping: shown while it works, not kept). `lib/assistant/activity.ts` is the one place that defines them. Steps are recorded by the code that does the work (`ResearchSession.searchWeb` and `fetchPage`, `prepareStudy`, `reviewAnswer`, `finishStudy`, the upload reader and the upload search) and reach the page **while that work runs** (`withActivity`), including inside a tool round and the checks after the draft. A step never carries a search query, a page's text, the model's reasoning, or an internal address. Labels are short fixed wording chosen on the server.

**Sources.** A page that was read is listed with its title, site, a plain-words tier ("primary text", "education site", "revision site"...) and how it was read, and is linked. The link is sanitised by `safeSource`: public `http(s)` only, no login in it, no fragment, never a local or internal address; the query string is kept only where it is part of the page's address (`?id=12`, `?act=3&scene=1`), and tracking parameters, anything that looks like a search phrase, a session, a token or an email address are dropped. A link that would be too long is never cut part-way (it falls back to the page without its query, then to the site). A page the fetcher will refuse is never named, not even in the "Reading..." step that precedes the refusal. The source list replaces the old appended "Sources read" text: the answer itself holds only the answer (and the "Check:" notes, below).

**When the answer appears.** Ordinary chat (greetings, simple questions, voice) streams as before. A *verified* answer (one answered from sources, in any subject that is read up on, or a quotation check) and an *advanced* one (a hard problem or a substantial exam task) is **held**: the draft is generated and checked, and the student reads **one complete answer**, delivered as a single `delta` with `whole: true`, after every check has finished and with the notes the checks add (what could not be verified, a calculation that did not check out, a note that no sources could be read) already in it. A rejected draft is never sent, and a draft is never released because the turn was interrupted. For a set text or history, and for a hard maths or science answer's working, the held draft also goes through the gate (`gate.ts`): a wrong quotation, an unsupported event or a wrong step is repaired by the model (twice at most) and, if still wrong, cut or flagged. Other held answers are checked (quotations, names against the pages read, working by calculation) and their problems are named under the answer, never silently cut: the events-and-characters check is written for stories and is not run on a biology explanation. If the checking itself fails, the student gets the fixed "I could not finish checking" words, not the draft. If the preparation (research set-up) fails, the turn is still classified and still held, and the note says no sources could be read: a failure never turns an answer that must be verified into one streamed unchecked.

**How a turn ends.** The stream always ends with `done` or `error`. The page treats a stream that ends without one as an interruption ("We lost the connection before the answer was finished"), however cleanly the connection closed, and settles the panel as failed, not completed. Stop, an error and a disconnect all end every step still running (as failed), remove the waiting message when nothing was shown, and leave no spinner. Closing the connection also ends the work on the server, and whatever had been shown is still stored (`settle` in `service.ts` runs once, whether or not anyone is still reading), so a stopped answer is there when the chat is reopened; a held answer that was not yet released is not stored. The summary row says only what is true of the steps: "Research and verification completed" needs a page that was read and at least one check that ran, with none failed; otherwise it says "Research completed", "Sources read, but some checks could not finish", "Sources could not be reached", "Checks completed", "Could not finish checking" or "Stopped". It folds by itself when the turn finishes (what the student opened or folded themselves is left alone) and opens again to show the steps and sources. The only moving thing is one small ring in the panel's heading, and not under reduced motion.

**Kept with the answer.** The finished steps (at most 24, 6,000 characters, details shed first) are stored with the assistant message in `chat_messages.activity` (migration `0016_chat_message_activity.sql`; apply it before relying on this against an existing database, since researched answers need the column) and read back, checked again, by `GET /api/assistant/sessions/:id` as `activity` (with `activityOutcome: "stopped" | "failed"` only for a turn that did not complete, so a reopened chat does not call it completed). It is deleted with the message (30 days, or with the chat). It holds labels, counts, page titles and links: never a query, reasoning, a rejected draft, a page's text, or an internal address. Small talk and simple questions have no panel once they are over.

**The model.** The same pipeline serves every model, local or picked: MiniMax and Step 5 give the same steps and the same single delivery, and their reasoning (which the providers keep apart from the answer) never reaches the page or the store. When research is on, the model is told to write only the answer: the panel shows what was searched and read, so the answer does not narrate it.

**Tests.** `tests/assistantActivity.test.mjs` and `tests/assistantDelivery.test.mjs` (events match real operations, sources really fetched, no draft leak, whole delivery, preparation failure, Stop, late lookups and tool rounds live, source-link rules, outcome record, both hosted models); `tests-e2e/ui-activity-panel.spec.ts` (every state, a live turn moved one event at a time, keyboard, axe light and dark, 360 px, motion); `tests-e2e/study-buddy-activity.spec.ts` (the real chat on the mock-provider server: one indicator inside the answer, the box does not move, one complete delivery, Stop, a cut-off stream, a server error, a reopened chat, a phone, axe while working); `tests-e2e/ui-ai-input.spec.ts` (the input draws no indicator of its own). The e2e specs run with no search service, so they show the honest "could not be reached" state; reading real pages needs the SearXNG and Crawl4AI services (see RESEARCH.md) and was not exercised in a browser here.

## The Paper Tutor (worked solutions written onto a paper)

With a PDF or photo of a maths paper in the box, **Solve this paper** reads it, lists the questions it found (tick the ones wanted), and writes worked solutions onto a copy in blue handwriting-style ink. Three ways to write them: **answers and working** (the default: the answer and as much working as fits in each answer space, the full method on pages added at the end), **answers on the paper**, or **worked solutions** (the paper untouched, then the pages). It runs as a background job, so the chat stays usable; the panel shows each question as it goes, then a download (`GET /api/assistant/files/<id>?download=1`, only for the family that owns it) and a preview of each page. A summary is posted into the chat with the paper attached, so "explain question 3" works afterwards without solving again.

How it decides what to write (`src/lib/paper/`):

- `questions.ts` finds the numbered questions from the text layer and measures the empty space below each from a drawing of the page: ink rows are obstacles, a solid rule (an answer box's edge) splits the space, a dotted answer line is somewhere to write. Pages with no text layer are read by the vision model instead, and marked "read from a picture".
- `solve.ts` asks the model for a structured solution (JSON, validated, one retry). **The model never certifies its own answer.** `maths.ts`, a small safe parser (no `eval`), checks it: against the equation, expression or calculation printed in the question first, and only then against a check the model proposes. A failed check triggers one second attempt with the model reasoning first and told exactly what did not hold; only an answer that a calculation confirms replaces the first.
- Every question ends with one status, shown in the panel, on the paper and in the summary: **checked by calculation**, **checked against the AI's reading** (the check passed, but on the AI's transcription rather than the printed text), **not checked** (nothing to calculate, for example a word problem), or **not confidently solved** (the check disagreed, or the model could not answer).
- `annotate.ts` writes only into measured empty space, never over printed text and never below 11 pt (what does not fit goes to the worked pages, with a page reference on the paper). Maths is typeset by MathJax as vector shapes; the handwriting font is Patrick Hand (OFL). Every page carries "AI-generated worked solutions - may contain mistakes". The output is read back before it is stored, to prove it opens.
- `jobs.ts` keeps jobs in the database (`paper_jobs`, migration 0012), not in the server's memory: the state, the questions found and **one checkpoint per finished question** are saved as they happen, a heartbeat renews the worker's lease, and a job whose worker has gone (a restart, a crash) is taken over on the next request and carries on with the questions that have no checkpoint. One job at a time per family is a database index, not only a rule in code; 10 papers a day; cancellable from any process; every model call goes through the same queue as the chat. Jobs and their checkpoints are kept 7 days (the uploads' retention) or until the chat is deleted. A question being solved when the process died is solved again from the start; the paper is re-read on recovery; the summary is posted after the PDF is stored, so a crash between the two can post it twice.
- Real paper structure (`questions.ts`): parts `1(a)(ii)` are found in sequence and each part is solved on its own with the words it shares as its stem; ids are opaque (`q1`, `q2` in paper order) and the printed label is kept; a question that runs onto the next page keeps its text; the cover, a formulae sheet and a blank page are not searched (so "1 hour 30 minutes" is not question 1), and the panel says which pages were skipped.
- **What counts as a task** (`questionTree.ts`, one rule for a text layer and a vision reading): a question with parts is the shared context of its parts, so a screenshot of "3" and "(a)" offers ONE task, `3(a)`, whose text carries the shared words, **unless the parent asks something itself** (a question mark, printed marks, or an instruction with something to work on, such as "Work out 2 + 3."): then it is a task too, listed before its parts with its own id, and its parts still carry its words as their context ("Factorise fully.", "Work out:" and "Work out the following." are shared instructions, not tasks); nested parts carry every level above them; an independent whole question stays; the same label appearing again starts a separate group (two sections both numbered from 1 are never merged); a part listed on a later page without its question inherits the shared words of the same group only. A page read from a picture is listed as a tree (`listing.ts`); a model that files a part's own sentences under the question is corrected. **Printed marks** are read in their own look at the page, not taken from the listing (a combined request misread "(4)" as 2), and kept only if there are exactly as many as tasks; otherwise they stay unknown.
- **A solution must be finished** (`completion.ts`), whatever the schema said and whether or not a calculation could test the answer: it flags instructions where working should be ("Calculate the area"), too little working for the marks, no conclusion in words with its reason where the question asks one, a yes/no question not answered Yes/No, arithmetic that is false (including lines with units; a stated rounding such as 6.18 for 68/11 is true), comparisons that are false, a "has enough" question without the figures compared, a Yes/No that contradicts the solution's own figures, a measurement with no unit, and (text pages) a "given" that is not in the question. The problems are of two kinds. **Work** (missing or false working, no conclusion, a contradiction) is mathematical completeness and makes a solution partly worked. **Detail** (only the machine-readable comparison of a "has enough" answer) never does: the comparison is derived from the working when the working already sets two quantities in one unit against each other (the decision says which is available and which is needed), asked for once, in a bounded repair that may only name figures the working shows, or left out, and a complete solution is not called partial because a field is empty. What a student sees is a plain sentence per problem ("One line of the working does not add up."), never a field name or a retry instruction. Each work problem is told to the model on a bounded retry (at most 3 attempts, the later ones reasoning first, all cancellable). If it still fails, the question is shown as **partly worked** ("Partly worked: not finished or not consistent, so look it over"), and an answer that its own working contradicts is not shown. "Unchecked" never hides an incomplete solution. A reference solution used for marking is only held to truth and self-consistency, not presentation.
- **A second look at a picture** (`PAPER_CROSS_CHECK`, default on): a calculation can show that the arithmetic follows from the figures the model read, but not that it read the diagram right (a wrong side of a shape gives tidy, consistent, wrong working). So a task read from a picture that otherwise passes is solved a second, independent time, reasoning first and not told the first answer; the two must reach the same decision or value. If they differ a third decides; with no majority nothing is presented as the answer ("partly worked", with the reason). Agreement is said in the note ("A second, independent attempt reached the same answer"), and the status stays "not checked by calculation": agreement is evidence, not proof. Text tasks and the reference solutions used for marking are not doubled.
- **Carrying context between uploads** (`context.ts`): in one chat, uploading 3(a), getting its answer, then 3(b) as a picture of the part only links the new part to the earlier upload: it is solved with the shared words, the original page (so the diagram is seen again, selectively: one page, not the history) and the earlier results offered as claims to re-check ("their arithmetic was checked but their reading of the diagram was not"). A link is made only when the part arrives WITHOUT its own shared words, from the same chat and owner, and exactly one earlier group of that number has shared words. Questions are told apart by their shared words with a high overlap, not equality (a model reads the same page a little differently each time). For each part the **active** answer is its latest revision that is an answer, kept with the upload, question and revision number it came from; the answers it replaced stay in the context's history and in the store, and are never shown to the solver or used by a check. The link is refreshed from the current answers when the part is solved (a correction may have arrived since it was read, or in another process), and a result checkpointed on an older answer is not restored over a correction. Two earlier question 3s is ambiguous (nothing is merged and the notice says so); none is "missing" (nothing is invented: the solver is told the facts were not provided and answers "not confidently solved" rather than guess). The link is saved with the job (`paper_jobs.questions`), so a reload or a recovery solves it the same way. "Does this change your answer?" is checked against the new and earlier decisions from the solution's own figures.
- **Handwriting** (`handwriting.ts`): the prose is Patrick Hand and so is the maths. MathJax still lays out every formula (fractions, roots, powers, spacing), but each glyph it places is swapped for the same character from the handwriting font, in the box MathJax gave it; a glyph the font lacks keeps MathJax's outline. Fractions are written at full size, nothing is wobbled, and the three modes' placement rules are unchanged. A conclusion is written under the answer.
- **Budgets for solving** (`PAPER_CONTEXT`, `PAPER_MAX_TOKENS`, `PAPER_REASONING_TOKENS`; defaults 8192 / 1800 / 3600): a page picture, the written-out working and a reasoning retry do not fit 4096, and 900 tokens and 8 steps truncated valid four-mark solutions (now 14 steps). The context follows the profile the server runs: a value different from `ASSISTANT_CONTEXT` reloads the model once when work changes between chat and paper, so keep them equal if both are busy. The queue, cancellation and the one-job-per-family limit are unchanged.
- Real-model proof (`apps/web/scripts/paper-live-check.mjs`, `npm run paper:live`): the owner's Q3 through the job pipeline in all three modes, then 3(b) in the same chat; the expected figures live in that checker, never in the solver's prompt (a test asserts the prompt carries none of them).
- Verification (`mathsEvidence.ts`): numeric agreement, completeness (`x = 2` for `x² = 4` works and is NOT the whole solution set), working consistency, and answer form (exact against rounded, the decimal places asked for) are kept apart; a right answer reached through a step that does not follow is left for review.
- Scanned pages (`layout.ts`): the vision model proposes where the answer space is, with a confidence; the proposal is checked against the drawing of the page (inside the page, big enough, empty, not over the question or another question's space) and refused with a reason if any check fails. `PAPER_SCAN_LAYOUT=false` turns it off.
- Benchmark: `docs/PAPER_BENCHMARK.md` (`npm run paper:bench`).

Measured with `qwen3.5:9b` on Ollama (`node --import tsx apps/web/scripts/paper-check.mjs`, and through the routes on a running server): the 5-question, 3-page GCSE fixture was read in about 3 s and solved in about 43 s with the model already loaded (about 3 minutes on a cold first run) on the 8 GB GPU. Across four runs through the routes every final answer was right; the statuses vary a little with the model's wording (the percentage question is sometimes "checked against the reading", sometimes "not checked"). Simultaneous equations sometimes need the reasoning retry (about 36 s against 6 s). Two checker faults found this way were fixed: "0.000 52" (a UK digit-group space) was read as 0 × 52, which marked a right answer "not confidently solved"; and sentences written in the maths field were typeset as maths. Output: `docs/screenshots/paper-tutor/`. Marking a student's own answers is the next section; it is opt-in because it has not been measured on real handwriting.

## Checking a completed paper (opt-in: `PAPER_MARKER_ENABLED=true`)

**Check my completed paper** appears next to **Solve this paper** when the switch is on. The student uploads a paper they have already written on (a PDF or a photo), optionally a mark scheme and the blank question paper as further PDFs in the same box (each marked "the mark scheme" or "the blank question paper" in a menu; nothing is assumed), picks the questions and the AI checks them. It is the same background job and panel as solving (`kind: "mark"`; `POST /api/assistant/papers { fileId, sessionId, kind: "mark", schemeFileId?, blankFileId? }`, then `/solve`), so the one-job-per-family rule, the daily cap, cancelling and the per-family ownership all apply, and every model call goes through the shared queue.

How a verdict is reached (`src/lib/paper/mark.ts`; the same rule as solving: **a calculation decides, never the model**):

1. **Read**: the vision model transcribes what the student wrote for the question from a picture of the page (answer, working, and how legible it was). It is told to copy, never correct.
2. **Reference**: the question is solved independently by the same solver and the same calculation check, **from the question alone** where possible: the blank question paper if the student gave one, else the printed text of the page, else the picture of their page with the handwriting to be ignored. The assessment records which.
3. **Compare**: the student's final answer is compared with the reference by calculation (values, solution sets in any order, equivalent expressions). A verdict needs a legible answer **and** a reference a calculation confirmed. Blank, unreadable, ambiguous and wrong are different states: a blank answer is a real zero; an unreadable one, a reading the AI doubted that disagrees with the reference, no clear final answer, or an unconfirmed reference are **needs checking** (their marks are *pending*, never zero, never wrong). A right value in the wrong form is **partly right**.
   **Feedback** is only for wrong or partly right answers, and only from working the student actually shows: with no working the AI does not guess a cause (the first real-model run invented "added instead of subtracted" for a digit swap); it says so and asks for the steps. Mark-scheme text, when supplied but not confirmed as this paper's, is context for the feedback only.
4. **Criteria and awards** (`assess.ts`, `scheme.ts`): the marks are awarded criterion by criterion. With a mark scheme that was **checked against the paper** (paper code, tier, session, question parts and marks; a contradiction refuses it, an unconfirmable identity leaves it unused for marks) the scheme's own M/A/B criteria are applied, each keeping where it came from (`scheme p.4, 2(a), M1`). Without one, an explicitly **provisional rubric** is built from the printed marks and the checked reference and labelled AI-estimated. No printed marks and no scheme: no maximum is invented; the question gets feedback only. The model proposes which criteria the working earns, **citing the numbered lines of the student's writing**; code then enforces: no cited line, no credit (it goes to review); the final-answer mark is decided by calculation; a dependent mark needs its parent; a follow-through mark with a wrong final answer goes to a person; a right answer with no working shown leaves the method marks pending; a wrong answer with no working earns none. Method marks survive a wrong final answer; they are not given because the final answer is right.
5. **Totals**: three numbers kept apart: marks on the questions fully assessed (awarded of possible), marks still waiting for a person (not counted as zero), and everything the chosen questions carry. Nothing is labelled as an official mark: the panel, the chat message and every page of the PDF say "AI-estimated" (or "provisional").
6. **Corrections and review**: the student (or their guardian) can correct how the AI read any question; it is assessed again against the same reference and criteria, the change is a new version (the AI's own is kept as version 1; `paper_assessment_versions`, append-only), the marked PDF is rebuilt and a note goes into the chat. A tutor may review a question's marks (`/api/tutor/papers/<id>/review`) only for a learner on one of their active assignments; their decision replaces the AI's marks in the totals and the AI's assessment stays in the history.
7. **Release flag**: numeric marks are behind `PAPER_MARKS_RELEASED` (development on unless `false`; production only if exactly `true`). Off, the work is still read, checked and given feedback, but no mark, award or total appears anywhere (panel, chat, PDF). The flag is a decision for the owner and should follow the validation in `docs/PAPER_BENCHMARK.md`, not precede it.

The output (`markPdf.ts`) is the student's own pages exactly as uploaded, a tick, cross, tick-and-dot or circle in the left margin beside each question the AI could place (only where the paper has a text layer saying where the question is, and never over the work), and feedback pages at the end. The summary with the feedback is posted into the chat with the paper and the mark scheme attached, so "where did I lose marks?", "give me a hint for question 4" and "explain question 2" work afterwards without checking again. The panel lists every question to open one by one.

**Measured** (`node --import tsx scripts/mark-check.mjs`, the default `qwen3.5:9b` on Ollama, 2026-10-22): on two **synthetic** papers (answers drawn into the answer spaces of the fixture papers in a handwriting-style font, then rebuilt as picture-only PDFs, so there is no text layer, as a scan would be), 7 questions with known right and wrong answers: questions found 7/7, the writing read correctly 7/7, verdicts given 7/7 and all 7 right, 0 right answers called wrong, about 30 s for 2 questions and 105 s for 5. The same run found a real fault, now fixed and tested: a student's letter x for "times" (`5.2 x 10^-4`) was read as a variable, so a right answer was called wrong; a digit-x-digit is now a multiplication, and two answers that use different unknowns get no verdict at all. (`qwen3-vl:8b-instruct` also scored 7/7 on the first run, before that fix, which that set did not expose because it read the sign as `	imes`.) **This is not evidence about real handwriting**: a font is tidier than a pen, there was no crossing out, no rough working, no photograph taken at an angle and no real exam-board mark scheme. Marking stays opt-in until it is measured on real scripts with a teacher's marks as the reference.

Known limits: a mark scheme must be a PDF with a text layer (a photo of one is not read, and the panel says so); scheme layouts differ between boards and the text is messy, so rows are read defensively and a part whose criteria cannot be read goes to review instead of being invented; the scheme path has been run with synthetic schemes only, **never a real exam-board mark scheme**; follow-through and dependency rules are applied conservatively (a person decides); geometry and diagram questions have no calculation check, so they are "needs checking". **Automatic marking has not been validated against work marked by a qualified person**: no human-marked handwriting exists in this repository, so the marker is UNVALIDATED (see `docs/PAPER_BENCHMARK.md`) and its marks stay behind `PAPER_MARKS_RELEASED`.

## Switching it off

`ASSISTANT_ENABLED=false` (or unset in production): the menu item disappears, the page says it is not available, every `/api/assistant/*` route answers 503 `unavailable` and no model is contacted. No redeploy of code is needed, only the environment variable.

## Who may use it

- An account with Library access (enrolled student or subscriber), signed in.
- **Adults only until `ASSISTANT_MINORS_APPROVED=true`.** Until then the first message needs a recorded tick ("I am 18 or over, and I am the person using LearnThrive AI", consent kind `assistant_adult_use`, version `2026-10-draft-2`: the name inside the wording changed on 26 October 2026, so the version moved with it and an older tick does not count as agreement to the new words). The account must also be an adult account holder (`adult_required` otherwise), and a student profile is not attached to a chat until the minors gate is open. The wording is a draft for the owner's lawyer.
- In production it also needs `ASSISTANT_ENABLED=true`, `ASSISTANT_PRODUCTION_APPROVED=true`, provider `custom` and a base URL and key. Ollama Cloud and the mock never qualify.

## What is kept, and for how long

| Data | Kept | Removed |
| --- | --- | --- |
| Chat text (questions and answers) | 30 days after the chat's last message | by the retention job; or at once when the family deletes the chat (hidden immediately, removed by the next run) |
| The activity record of an answer (steps, page titles and sanitised links, no queries or reasoning) | with its message: 30 days after the chat's last message | by the retention job, or when the chat is deleted |
| Uploaded pictures and PDFs, and the Paper Tutor's annotated PDFs | 7 days, or when the chat is deleted | by the retention job (storage objects first, rows only if every object went) |
| Paper Tutor jobs (the questions found, progress, and each question's solution or marking) | in the server's memory, 2 hours after last use | on restart, or when they expire |
| Usage counters | counts only, no text | rolling |
| Safeguarding flag | an opaque reference, a category, a short excerpt in the email to the lead | the lead's own record; nothing named is stored in the app |
| Audio (voice) | never stored | n/a |

Run the retention job daily: `npm run assistant:retention` (a cron on Render; it needs the same Supabase and storage variables as the site). Families can see, export (JSON, `GET /api/assistant/export`), delete a chat, or delete all chats from the LearnThrive AI screen. The chat rows go with the family record (database cascade), but **uploaded files in storage do not**: before a family's record is erased, run "Delete all my chats" for it and let the retention job run once, so the files are removed while their paths are still known. Wiring that into the account-deletion procedure is listed in [RETENTION_AND_DELETION.md](RETENTION_AND_DELETION.md).

## What was not tested here

- A real production provider: none has been chosen (plan19 section 6 decides it: data processing agreement, no training on inputs, a suitable processing location, EU or UK if possible).
- A real child, a real safeguarding lead, a real teacher marking panel: the evaluation is synthetic and rule-based, so it ranks models; it is not evidence of pedagogical quality.
- Handwriting: the vision set is typed text only. The Paper Tutor was measured on generated papers (typed, one scanned page), not on real exam-board papers or phone photos of them.
- The email path to a real mailbox (the dev outbox is used in tests).

## Decision record: Beam, and how to go back

- **Why Beam:** one hosted reasoning model with tool use, in place of three local ones. The GPU is free, the same model serves chat, interactive answers and the checks, and nothing local has to be warmed, kept resident or kept in step. It is an open model from Reflection (about 501B parameters, 23B active, a 1M-token context, text only), served through Ollama Cloud.
- **What it costs:** Ollama's pages say a free account is enough to call the API and that usage is shown at ollama.com/settings/usage; they publish no rate limit. Any promotional free period is not a permanent zero-cost guarantee. The daily token budget (`ASSISTANT_DAILY_TOKEN_BUDGET`) and the per-minute and per-day message caps stay on, and every request of a turn is counted.
- **What it cannot do:** read a photo or a scanned page (text only), and it is not approved for children or for production. Those gates are unchanged: `ASSISTANT_MINORS_APPROVED`, `ASSISTANT_PRODUCTION_APPROVED` and a `custom` provider chosen under plan19 section 6.
- **Not measured here:** whether Beam writes valid interactive interfaces reliably, and how often. The scripts and tests prove the code with a scripted stand-in; the live measurement needs an `OLLAMA_API_KEY` and is described in [OPENUI.md](OPENUI.md).

### Rolling back

- **To a local model:** the local provider (`ollama.ts`) is kept in the repository only for the Paper Tutor and voice benchmark scripts. To run the assistant on a local model again, check out the commit before this change (`git log --oneline -- apps/web/src/lib/assistant/providers.ts`): the picker, the chain, the helper models and `scripts/ollama-local.mjs` all live there.
- **To plain text only:** set `OPENUI_ENABLED=off`. Every answer is then text, exactly as before; nothing else changes.
- **To another hosted model:** the `custom` provider takes any OpenAI-compatible endpoint (`ASSISTANT_BASE_URL`, `ASSISTANT_API_KEY`, `ASSISTANT_MODEL`); it is also the only provider production accepts.
