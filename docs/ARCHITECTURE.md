# Architecture

## Starting point (before this migration)

Two separate repositories:

- **`D:\LearnThrive`** — the real, live LearnThrive Tuition marketing website. Next.js 16 (App Router) + React 19, TypeScript, no database, no authentication. A `POST /api/enquiry` route sends booking-consultation emails via Resend. Its footer links to a real, external, already-in-use TutorCruncher account for tutor login. Content/link tests via Node's built-in test runner (`node --test`); a browser/accessibility check script using axe-core against a locally installed Chrome/Edge.
- **`D:\LearnThriveSoftware`** — the classroom prototype covered by this repository's own earlier plans (`plan.md` through `plan4.md`, gitignored/private). Vite + React 19 client, Express 5 + Socket.IO 4 signalling server, a hand-rolled WebRTC mesh (1 tutor + up to 3 students), a collaborative Excalidraw whiteboard, Cloudflare Realtime TURN credential generation, and extensive classroom moderation (polls, understanding checks, timers, announcements, a Help Queue). 89 Vitest tests, 20 Playwright scenarios × 2 browsers. No accounts, no persistence — everything lives in an in-memory `Map` per room and resets on server restart.

## This migration (Phase A — repository convergence)

Both became workspace members of one npm-workspaces monorepo at `D:\LearnThriveSoftware`:

```
D:\LearnThriveSoftware
├── apps/
│   ├── web/         Next.js — public site now, +platform UI from Phase B onward
│   ├── classroom/    Vite + React — the real-time classroom, unchanged in behaviour
│   └── realtime/      Express + Socket.IO — the classroom's signalling/TURN backend
├── packages/
│   └── shared/        shared/protocol.ts + shared/allowedHosts.ts, now @learnthrive/shared
└── docs/               this document and its siblings
```

`D:\LearnThrive` was read from, never written to — the plan behind this migration is explicit that it stays read-only source material. Its `src/`, `public/`, `next.config.ts`, `tsconfig.json`, `eslint.config.mjs`, and test suite were copied into `apps/web` verbatim; nothing was redesigned in the process (see "What changed in the copy" below for the small, necessary exceptions).

### Why four workspace members, not one

The plan behind this migration states four boundaries as **mandatory**: web application, realtime/classroom service, domain/data access layer, and shared models/permissions must all be genuinely separable, not just organised by folder convention inside one app. An npm workspace gives each boundary a real package boundary — its own `package.json`, its own dependency graph, its own lint/typecheck/test/build lifecycle — so "separate" is enforced by tooling (a workspace can only import another workspace's code via that workspace's declared package exports, e.g. `@learnthrive/shared/protocol`), not just by developer discipline.

`packages/data` (the domain/data-access layer named in the plan's illustrative tree) doesn't exist yet — it's introduced in Phase C alongside the domain model and repositories, once there's an actual domain to model. Introducing an empty package now would be scaffolding without substance.

### Why the classroom wasn't rewritten into Next.js this pass

The plan's own preferred long-term direction is Next.js as the primary LearnThrive web application, with the classroom UI eventually migrated into its authenticated area. This migration deliberately did **not** attempt that rewrite in the same pass as the structural monorepo move, for a concrete reason: `apps/classroom` is a large, working, extensively-tested real-time application — a hand-rolled WebRTC mesh with per-peer bandwidth policy, a lazily-loaded Excalidraw whiteboard with a custom reconciliation protocol, and 20 Playwright scenarios that exercise real getUserMedia/WebRTC/Socket.IO behaviour end to end. Rewriting that into React Server Components / Next.js's client-component boundaries at the same time as moving every file on disk would combine two large, independently risky changes into one, with no way to isolate which one caused a regression if something broke. The plan itself warns against exactly this: "If some classroom code genuinely needs to remain in its current Vite application temporarily, introduce a migration boundary rather than destabilising it."

So `apps/classroom` stays a Vite app for now — the "migration boundary" is architectural (a separate workspace, entered from the platform via an authenticated route once Phase E builds that integration) rather than a rewrite. Every classroom test (89 Vitest + 40 Playwright runs) was re-verified passing after the move, unmodified in what they assert.

### What changed in the copy

Almost nothing behaviourally. Specifically:

- **Import paths**: `shared/protocol.ts`/`shared/allowedHosts.ts` moved to `packages/shared` and are now imported as `@learnthrive/shared/protocol` / `@learnthrive/shared/allowedHosts` (a real package import, resolved via the workspace's `node_modules` symlink) instead of relative paths like `../../shared/protocol`.
- **Split `package.json`/`tsconfig.json`/`vitest.config.ts`/`eslint.config.js`**: each app now owns its own, scoped to only its own directory, where before one root config covered both the Vite client and the Express server.
- **A dependency-hoisting bug found and fixed during this migration**: `@excalidraw/excalidraw`'s own transitive dependencies (several `@radix-ui/react-*` packages) have a hard (non-peer) dependency on `react@18.3.1`. In a flat, non-workspace install this hadn't surfaced. Once `apps/classroom` became a workspace member with no direct `react` dependency declared at the *root* `package.json`, npm's hoisting algorithm picked React 18.3.1 for the top-level `node_modules/react` slot (outvoted by sheer number of radix-ui subpackages) and nested a second copy of React 19.3.0 inside `apps/classroom/node_modules` to satisfy the app's own direct dependency — two React copies at runtime, which crashed the whiteboard specifically with "Invalid hook call" the moment Excalidraw rendered. Fixed with an `overrides` pin at the root `package.json` (`"react": "^19.3.0", "react-dom": "^19.3.0"`), forcing one resolved copy everywhere in the tree. Caught by re-running the full Playwright suite after the move, not assumed safe — see the verification note below.
- **Two small, faithful bug fixes in the migrated marketing site** (`apps/web`), both proven pre-existing in the real `D:\LearnThrive` repository by running its own unmodified `npm test` before touching anything: (1) four ESLint findings (two `<a>` tags that should be Next's `<Link>`, one unescaped apostrophe, one effect that set state synchronously — restructured into a lazy `useState` initializer) that a fresh dependency install surfaced via a newer `eslint-plugin-react-hooks` rule; (2) the enquiry API route constructed its Resend client at module load time, and a `resend` patch release (6.28.0 → 6.28.1) started throwing synchronously on a missing API key at construction — breaking the route's own test suite's stated intent ("route loads without email credentials and returns 503"). Fixed by reading the API key and constructing the Resend client at request time inside the handler, exactly matching what the test file was already asserting. Pinned `resend` to the exact `6.28.0` from the original lockfile as well, though the request-time fix is what actually resolved it.

None of these change what a visitor or a classroom participant sees or experiences — they're infrastructure/dependency-resolution fixes and pre-existing bug fixes surfaced by the migration, not redesign.

## Phase B — auth foundation

Adds `apps/web`'s `/login`, a development-only in-memory credential store (five fictional seed accounts, scrypt-hashed passwords), server-issued sessions (HTTP-only cookie, validated server-side against an in-memory session store, never trusting the cookie's mere presence), and role guards (`requireSession`/`requireRole`/`requireRoleForApi`). A minimal `/dashboard` shell renders role-differentiated placeholder copy; `/dashboard/admin` is the first real role-restricted route, proving the guard mechanism end to end. See `docs/AUTHENTICATION.md`, `docs/ROLE_PERMISSIONS.md`, and `docs/DEVELOPMENT_ACCOUNTS.md`.

Two real bugs found and fixed while building this phase's own test coverage (both in the *tests*, not the app, caught by the tests failing loudly rather than passing on a false premise):

- Next.js 16's dev server treats `127.0.0.1` and `localhost` as different origins and silently returns 403 for `/_next/static` chunk requests from `127.0.0.1` — which meant zero client JS loaded and every button/form on the page was inert, with no visible error banner. The Playwright config's `baseURL`/`webServer.url` needed to be `localhost`, not `127.0.0.1`.
- The login E2E test helper's `.click()` on the sign-in button only waits for the click event to dispatch, not for the async fetch-then-`router.push()` chain it triggers — a caller's next `page.goto()` could race ahead of the actual login completing. Fixed by waiting for the resulting URL change alongside the click.

Verification: 21/21 Node `--test` unit tests (password hashing, dev credential store — valid/invalid/unknown/disabled login, case-insensitive email) + 12/12 Playwright E2E scenarios (login, logout, session persistence across reload, role-gated route access proven for Tutor/Client/Admin, already-authenticated redirect, password show/hide, empty-submission validation) — all against a real running `next dev` server (not `next start`; see `docs/AUTHENTICATION.md`'s production-safety note for why). Full workspace lint/typecheck/build still pass, and all 18 original marketing routes remain statically prerendered — the new auth-aware routes (`/login`, `/dashboard`, `/dashboard/admin`, the two `/api/auth/*` routes) are the only ones now server-rendered on demand, exactly as expected.

## Phase C — People and Tuition Assignments

Adds `packages/data` (the domain/data-access layer named as mandatory back in Phase A's boundary list, introduced now that there's an actual domain to model): `Tutor`, `Client`, `Student`, `ClientStudentLink` (many-to-many — a plan-specified requirement, not a 1:1 assumption), and `TuitionAssignment`, each behind a repository interface with one implementation today (`InMemoryDataProvider`, seeded with the plan's own demo scenario — Jamie Patel/Sarah Ahmed/Ayaan Ahmed/GCSE Mathematics). Admin-only pages for listing/creating people and assignments, using Next.js Server Actions for mutations (each re-checking `requireRole(["ADMIN"])` itself, since a Server Action is a callable POST endpoint independent of which page renders a form pointing at it). See `docs/DOMAIN_MODEL.md`.

Found and fixed one real bug in this phase's own test infrastructure: the `apps/web/tests/auth.test.mjs` TypeScript-loading helper (built in Phase B to load `devProvider.ts` without a compiled JS build step) only recursively transpiled *relative* imports; once `devProvider.ts` started importing `@learnthrive/data/inMemoryProvider` (a workspace package, also raw TS source with no compiled JS), that import fell through to real Node `require()`, which resolved the file via `node_modules` but then hit Node's own native TypeScript type-stripping — which doesn't support constructor parameter properties, a feature `packages/data`'s repository classes use. Fixed by extending the test loader to route `@learnthrive/data/*` specifiers through its own recursive transpiler too, anchored to a fixed, known path rather than re-derived per caller.

Verification: 6/6 new `packages/data` unit tests (repository CRUD, the many-to-many Client↔Student relationship, seed-data integrity), apps/web unit tests still 21/21, and 4 new Playwright E2E scenarios (Admin sees the seeded demo data, Admin adds a new Tutor, Admin creates a new Tuition Assignment, a Tutor is blocked from the people-management routes) — 16/16 alongside Phase B's existing 12. Full workspace lint/typecheck/test/build pass; the marketing site's 18 static routes remain untouched.

## Phase D — Calendar and Lessons

The largest phase so far. Adds `Lesson`, `RecurrenceInput`, and `TutorAvailabilityBlock` to the domain model, a `LessonRepository`/`AvailabilityRepository` pair, and a genuinely non-trivial scheduling layer at `apps/web/src/lib/scheduling/`:

- **Time zones** (`timezone.ts`): every `Lesson.startAt` is a real UTC instant; conversion to/from wall-clock time in `Europe/London` (the plan's stated default) uses only `Intl.DateTimeFormat` — no date-library dependency — and is correct across DST because it asks the runtime's own tzdata for the offset at the *specific* instant in question rather than assuming a fixed one.
- **Recurrence** (`recurrence.ts`): WEEKLY/BIWEEKLY/CUSTOM_WEEKDAYS, bounded end conditions, every occurrence materialised as its own independent `Lesson` row sharing a `recurrenceId` (required by the plan's "this lesson only / this and future / entire series" edit model, which a virtual/computed series can't support). Proven with a real DST-boundary test — a weekly series that crosses the actual 2025 British clock change keeps the same *local* time throughout while the underlying UTC instant shifts by an hour partway through.
- **Scheduling service** (`schedulingService.ts`): conflict detection (warns per plan section 30, never silently blocks), reschedule with all three edit scopes, and cancellation that records who/when/why without deleting the row.
- **Calendar UI**: FullCalendar (`@fullcalendar/react` 6.1.19 — the plan's own suggestion to use a real calendar library) giving Month/Week/Day/List views, drag-and-drop rescheduling with a scope-confirmation dialog for recurring lessons, and centralised role-based visibility (`visibleLessons.ts`) so Admin/Tutor/Client/Student each see only what they should.
- **IDOR protection**: the lesson detail page (`/dashboard/lessons/[id]`) independently verifies the requesting user is actually connected to *that specific lesson* — not just that the calendar happened not to show it to them — and redirects to `/403` otherwise. This is the adversarial case plan section 85 explicitly names ("Student joins unrelated classroom"), proven with a real end-to-end test that creates a wholly separate Tutor/Student/Assignment/Lesson and confirms an unrelated Student is blocked by direct URL.

Two real bugs found and fixed, both via the E2E tests failing loudly rather than being assumed away:

- **The conflict-confirmation form silently wiped its own required fields.** `useActionState`'s re-render doesn't itself repopulate a `<form>`'s *uncontrolled* field values (their `defaultValue` only applies on a DOM node's first mount) — so after a conflict warning appeared, clicking "Schedule anyway" resubmitted an empty form, which native HTML validation then silently blocked (no new network request at all, easy to miss without checking). Fixed by having the server action echo back exactly what was submitted, and remounting the form (via a `key` that changes when that echo changes) so the echoed values become the fields' new real defaults — not by turning every field into React-controlled state, which would have been a much larger change for the same result.
- **A test bug, not an app bug, but worth recording**: an IDOR test tried to log in as a second identity (a Student) without logging out of the first (Admin) — and `/login`'s own already-authenticated redirect (deliberately built and tested in Phase B) correctly bounced it straight to `/dashboard` without ever rendering the form, so the test hung waiting for a login field that was never going to appear. Fixed by having the test helper always log out first.

Verification: 6 new `packages/data` seed/relationship tests (Lesson-adjacent), 21 new `apps/web` unit tests (5 timezone + 10 recurrence including the DST case + 8 scheduling-service), and 10 new Playwright E2E scenarios (calendar visibility, single and recurring lesson creation, conflict warning + override, lesson detail access for Admin/Tutor, the IDOR block, cancellation, Tutor availability, Client-role calendar filtering) — 26/26 across all three `apps/web` Playwright spec files together. Full workspace lint/typecheck/test/build pass; `apps/classroom`/`apps/realtime`'s own 89 tests are unaffected. Running total: 137 unit/integration tests, 40 classroom + 26 web = 66 Playwright scenarios.

## Phase E — Classroom integration

Adds a signed, short-lived **classroom join token** (`packages/shared/classroomToken.ts`, HMAC-SHA256, `timingSafeEqual`-verified) as the one thing that crosses the trust boundary between the platform (`apps/web`, which knows accounts and Lessons) and the pre-existing classroom prototype (`apps/classroom`/`apps/realtime`, which has no concept of platform identity at all). `Lesson.classroomRoomId` — a fresh `crypto.randomUUID()` per lesson occurrence, never derived from or shared with the lesson's own id — is generated once at lesson-creation time. `joinClassroomAction` re-runs plan section 34's full checklist server-side (logged in, assigned to this specific Lesson, Lesson is `ONLINE`, not `CANCELLED`, inside the join window) before signing a 5-minute token and redirecting into `apps/classroom`; `apps/realtime`'s `room:join` handler verifies the token and — critically — uses only the token's own name/role/roomId for the join, never a client-declared value sent alongside it, which is what stops a modified client from claiming a different identity than the one the platform actually authorized. The pre-existing manual name/room-code entry path is left fully intact as a fallback (plan section 36). See `docs/CLASSROOM_INTEGRATION.md`.

The join window (plan section 35) is explicitly configurable, not hardcoded into the authorization check: a Tutor can join 30 minutes before start, a Student 10; both stay open 30 minutes past the scheduled end for a lesson that overruns (`apps/web/src/lib/scheduling/joinWindow.ts`).

`.env.example` files for `CLASSROOM_JOIN_SECRET`/`NEXT_PUBLIC_CLASSROOM_URL` could not be created in this pass — the sandbox denies writing any `.env*` path outright, even a template with no real secret in it. The exact variables and values are documented in `docs/CLASSROOM_INTEGRATION.md` instead; both apps fall back to the same hardcoded dev-only secret if unset, so local development works without any manual setup regardless.

Verification: 5 new `apps/realtime` tests (a valid token joins using the token's own identity even when different values are also sent alongside it; an expired token, a tampered token, and a token forged with a different secret are all rejected; the manual entry path still works unchanged) — 68/68 in that workspace. 5 new `apps/web` unit tests for the join-window boundaries (`joinWindow.test.mjs`) — 47/47 in that workspace. 4 new Playwright scenarios (Tutor sees a disabled Join control outside the window; Client never sees one at all; a `joinError` query param renders; existing IDOR/visibility coverage unaffected) — 13/13 in `lessons.spec.ts`. `apps/classroom`'s existing 40 Playwright scenarios and `apps/web`'s other two spec files are unaffected by the `meeting.ts`/`App.tsx` changes (verified by re-running them, not assumed). Full workspace lint/typecheck/build pass.

**Honestly not done in this pass**: no test drives the actual cross-app redirect end-to-end (Tutor clicks Join → lands in `apps/classroom` already admitted) with all three dev servers running together — the token sign/verify contract is proven at the `apps/realtime` boundary, the authorization checklist and join-window are proven at the `apps/web` boundary, and `apps/classroom`'s token-consuming code is typechecked and lint-clean, but nothing exercises all three at once. A manual pass through the live dev servers (`npm run dev`, both apps, a real Tutor login → Join Classroom click) is recommended before treating this as production-proven.

## Phase F — Attendance and Lesson Logs

Adds `LessonAttendanceRecord` (one per Student per Lesson — a group lesson's Students are marked independently) and `LessonActivityEvent` (a chronological, append-only audit timeline per Lesson) to the domain model, plus `apps/web/src/lib/attendance/attendanceService.ts` and `apps/web/src/lib/activity/activityService.ts`. `completeLesson()` enforces plan section 66's "do not prematurely set completed while mandatory fields are absent" — refusing (with a real, surfaced error, not a silent no-op) to mark a lesson `COMPLETED` until every Student has an attendance record. Activity events are now logged directly by the scheduling functions that cause them (lesson created, rescheduled with the exact "Changed from Tuesday 17:00 to Thursday 18:00" wording plan section 65 asks for, cancelled) as well as by attendance-marking and completion, so the lesson detail page's new Activity timeline is a real record of what happened, not a placeholder. See `docs/ATTENDANCE.md`.

Plan section 39's "auto session log" (classroom join/leave/reconnect events prepopulating attendance evidence) is **not built** — there is no event channel from `apps/classroom`/`apps/realtime` back to `apps/web` beyond the one-way join-token handoff built in Phase E, and building one is real infrastructure in its own right, not a small addition here. Attendance is entirely Tutor-entered this phase. Documented honestly in `docs/ATTENDANCE.md` and `docs/PRODUCTION_GAPS.md` rather than faked with a fabricated "Student joined" log line that no real event produced.

A real bug found and fixed while building this phase's own test coverage: the `apps/web/tests/_tsLoader.mjs` shared TypeScript-loading helper (built in Phase C, extended in Phase D) only recursively resolved relative imports and `@learnthrive/data/*` specifiers — the moment `schedulingService.ts` started importing the new `activityService.ts` via this app's own `@/*` tsconfig path alias, that import fell through to a real Node `require()`, which has no idea the alias exists, and crashed with `MODULE_NOT_FOUND`. Fixed by extending the loader with a third branch for `@/*`, resolved against `apps/web/src/` the same way the tsconfig itself defines it.

Verification: 6 new `apps/web` unit tests (`attendanceService.test.mjs` — recording a status and its activity event, upsert-not-append on a second mark, the new `CREATED` event, the completion gate refusing and then succeeding, a cancelled lesson never completable) and 4 new Playwright scenarios in `lessons.spec.ts` (join-control gating for Tutor/Client, the `joinError` query surface, and a full create → mark attendance → complete → activity-timeline flow) — 14/14 in that spec file, 30/30 across all three `apps/web` Playwright spec files. `packages/data`'s 6 tests unaffected. Full workspace lint/typecheck/test/build pass.

## Phase G — Lesson Reports

Adds `LessonReport` (one per Lesson, `DRAFT → SUBMITTED → APPROVED`) and `PlatformSettings` (a single well-known record holding `requireReportApproval`, overridable per `TuitionAssignment`) to the domain model, plus `apps/web/src/lib/reports/reportService.ts`. The Parent/Student visibility boundary (plan section 43: internal Tutor notes must never leak) is enforced in exactly one place — `visibleReportFor(viewer, report)` — which every page and action calls rather than reading `LessonReport` fields directly, so a caller can't accidentally forget to strip `internalTutorNotes`/`confidence`. Proven with a real end-to-end test that writes a report containing a literal `"CONFIDENTIAL: ..."` string in the internal notes, submits it, has an Admin approve it, then asserts that string never appears on the page when a Client views the same lesson.

`completeLesson()` (Phase F) now genuinely enforces `Lesson.reportRequired` (plan section 45) — a lesson can't be completed while its report is missing or still a `DRAFT`; a `SUBMITTED` report is sufficient (the plan says "until required report exists," not "until approved"). See `docs/LESSON_REPORTS.md`.

Verification: 11 new `apps/web` unit tests (`reportService.test.mjs` — draft creation/idempotency, edit-lock after submission, the required-summary check, both approval-required and approval-overridden-off submit paths, approve gating, and the visibility boundary at every status) and 1 new Playwright scenario covering the entire lifecycle (create lesson requiring a report → attendance → blocked completion → draft → submit → completion unblocks → Admin approves → Client sees the public summary but never the internal notes) — 15/15 in `lessons.spec.ts`, all other `apps/web` Playwright specs (`auth.spec.ts`, `people.spec.ts`) re-run and unaffected. `packages/data`'s 6 tests unaffected. Full workspace lint/typecheck/test/build pass.

**Not built this phase**: the Student progress timeline page (plan section 46 — `ReportRepository.forStudent()` exists to support it, but no UI reads it yet), report PDF export (plan section 47 explicitly defers this), a revision workflow for a submitted/approved report, and a settings page for `requireReportApproval` (the data-layer setting is fully respected but has no Admin UI). Documented honestly in `docs/LESSON_REPORTS.md`.
